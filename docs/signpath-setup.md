# SignPath 신청 및 연결 준비

이 문서는 무료 오픈소스 코드 서명 신청과 승인 뒤 배포 연결 절차를 정의한다. 현재는 지원 신청 단계다. 실제 재단 서명, 계정 설정과 연결 검증은 완료되지 않았다.

## 신청 자료

공식 신청 주소는 [SignPath Foundation 신청 양식](https://signpath.org/apply.html)이다.

| 항목 | 내용 |
| --- | --- |
| 프로젝트 | text-pad |
| 저장소와 홈페이지 | https://github.com/olivecrow/text-pad |
| 다운로드 안내 | https://github.com/olivecrow/text-pad#installation |
| 라이선스 | MIT |
| 분류 | 생산성 도구 |
| 유지보수 주체 | 개인 유지보수자 |
| 자동 빌드 | GitHub Actions, GitHub가 제공하는 Windows 실행 환경 |
| 서명 정책 | [Code signing policy](features/code-signing.md) |
| 개인정보와 외부 통신 | [개인정보 처리 및 외부 통신 안내](features/privacy.md) |

신청인의 이름과 연락 이메일은 공개 프로젝트 문서에 기록하지 않는다. 신청서 사본, 공개 다운로드 집계와 화면 증거는 Git 추적에서 제외한 `output/signpath/`에 보관한다. 다운로드 수는 파일별 다운로드 횟수이며 사용자 수나 실제 설치 수로 설명하지 않는다. 확인할 수 없는 평판이나 언론 보도를 작성하지 않는다.

## 제출 전 확인

- 이 문서와 서명 정책, 개인정보 안내를 공개 저장소에 반영하고 신청서의 링크를 실제로 열어 확인한다.
- 홈페이지와 다운로드 안내에 서명 정책을 연결한다. 승인 전에는 이미 무료 지원이나 재단 서명을 받고 있다고 표시하지 않는다.
- 저장소 소유자가 신청인과 담당 역할을 확인하고 GitHub의 2단계 인증 상태를 확인한다.
- 자동 업데이트 확인과 외부 이미지 요청을 포함한 개인정보 안내를 심사에 제공한다. 현재 설치 화면에는 이 안내와 자동 업데이트 확인 중지 옵션이 없으므로 재단의 요구를 충족한다고 단정하지 않는다.
- 신청인의 계정 정보, 필수 행동 규약 및 개인정보 처리 동의를 확인한 뒤 신청서를 제출한다. 선택적인 홍보 수신 동의는 신청에 필요하지 않다.

## 승인 뒤 필요한 정보

| 설정 | 보관 위치와 용도 |
| --- | --- |
| `SIGNPATH_ORGANIZATION_ID` | 재단이 지정한 조직 식별자. GitHub Actions 변수. |
| `SIGNPATH_PROJECT_SLUG` | 승인된 text-pad 프로젝트 식별 이름. GitHub Actions 변수. |
| `SIGNPATH_SIGNING_POLICY_SLUG` | 재단이 지정한 릴리스 승인 정책 이름. GitHub Actions 변수. |
| 파일 구성 식별 이름 | 실행 파일과 설치 파일 요청에 사용할 승인된 구성 이름. |
| `SIGNPATH_API_TOKEN` | 서명 요청 권한의 접근 토큰. GitHub Actions 비밀 값. 로그·문서·커밋에 기록하지 않는다. |

계정은 안내받은 초대 절차로 활성화하고 2단계 인증을 사용한다. 저장소 접근 권한이 필요한 SignPath GitHub 앱을 설치할 때는 필요한 저장소와 권한을 확인한다. 새로운 계정 자격 증명과 접근 권한은 사용자 확인을 거친다.

## 파일 구성 초안

- [실행 파일 구성](signpath/app-executable.xml): 압축 파일 최상위의 `text-pad.exe`만 서명한다.
- [설치 파일 구성](signpath/installers.xml): 최상위 NSIS 설치 파일과 MSI를 서명하며, MSI에 들어 있는 `text-pad.exe`는 기존 제작자 서명을 검증한다.
- 두 구성은 `version` 매개변수를 필수로 받고, 실행 파일과 NSIS의 제품 이름 및 버전을 제한한다. 버전은 해당 빌드의 제품 버전에서 읽는다.
- 구성의 XML 문법과 로컬 산출물 구조는 확인할 수 있지만 SignPath 서비스에서 수락됐다는 근거는 아니다. 승인 뒤 실제 샘플을 업로드해 생성된 구성과 대조하고 재단의 정책 및 스키마 검증을 통과해야 한다.
- MSI 안의 파일 경로, NSIS 내부 실행 파일과 제거 프로그램의 서명은 실제 설치와 추출 결과로 검증한다. 공식 파일 형식 목록은 NSIS를 내부 파일 서명이 가능한 형식으로 명시하지 않으므로 외부 설치 파일 서명만으로 완료 처리하지 않는다.

## 배포 연결 순서

현재 `.github/workflows/release.yml`은 빌드와 Tauri 업데이트 서명 및 공개 배포를 함께 수행한다. 재단 연결 전에는 이 작업에 미확인 식별자나 서명 완료 주장을 넣지 않는다.

연결할 때는 다음 순서를 유지한다.

1. 기존 소스·브라우저·Rust 검증을 통과한 커밋에서 실행 파일을 빌드한다.
2. 실행 파일을 해당 GitHub 실행의 보관 파일로 업로드하고, 실제 파일 식별자로 SignPath 서명을 요청한다.
3. 담당자가 수동 승인한 파일을 내려받아 제작자 서명, 인증서 체인과 시간 인증을 검증한다.
4. 서명된 실행 파일을 MSI와 NSIS에 포함한다. NSIS 제거 프로그램도 Tauri의 빌드 중 서명 연결로 처리할 수 있는지 재단과 확인한다.
5. 만들어진 설치 파일을 같은 실행에서 업로드하고 재단 서명 및 담당자 승인을 거친다.
6. 최종 설치 파일과 설치되는 실행 파일을 검증한 뒤 기존 Tauri 키로 업데이트 서명과 `latest.json`을 만든다.
7. 검증된 설치 파일, 업데이트 서명과 업데이트 정보를 같은 릴리스로 배포한다. 원래 업데이터 공개키를 변경하지 않는다.

신규 연결에 사용할 외부 GitHub Actions도 검토한 커밋으로 고정한다. 서명 요청은 파일 출처를 검증할 수 있는 공식 GitHub 연결을 사용하며, 로컬 빌드 파일을 이미 공개된 릴리스에서 다시 받아 출처 증명 없이 서명하지 않는다.

## 완료 기준

- 재단 신청 접수와 지원 승인, 계정 2단계 인증을 각각 확인한다.
- SignPath의 프로젝트, 파일 구성과 수동 승인 정책이 실제 승인된 값으로 설정돼 있다.
- 자동 빌드에서 실행 파일과 설치 파일이 재단 서명으로 만들어지고 검증된다.
- 실제 설치 결과의 실행 파일과 NSIS 제거 프로그램까지 검증한다.
- 최종 설치 파일의 Tauri 업데이트 서명도 기존 공개키로 검증된다.
- 공개 GitHub 릴리스에서 받은 파일이 검증된 파일과 일치한다.
